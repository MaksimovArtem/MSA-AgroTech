# ADR-006: Переход к SaaS

Автор: Максимов Артем

## 1. Контекст

В **ADR-005: Сравнение решений** было решено использовать решение, описанное в **ADR-002: Архитектура платформы и Edge для управления фермой**, в качестве MVP. 

## 2. Требования

Требуется расширить решение до SaaS платформы
Необходимо:
- Проработать несколько вариантов изоляции данных
- Добавить сервисы тарификации и биллинга
- Интегрироваться с российскими платежными системами
- Проработать API для SaaS
- Предложить финальную архитектуру решения

## 3. Решение

### 3.1 Изоляция данных

Рассмотрим 3 варианта изоляции данных:
-  На уровне схем БД
	Каждый тенант получает свой неймспейс в каждой БД. То есть, в БД пользователей останется users_db, но работа будет идти с tenant1.users_db, tenant2.users_db
	Низкоуровневые элементы Postgres, относящиеся к уровню одной базы данных, будут делиться между тенантами. А значит "тяжелый" запрос к одному из них - повлияет на все остальные. Ресурсы процессора и оперативной памяти также будут делиться.
	
- На уровне отдельных баз данных
	Каждый тенант получает свою базу данных в каждой БД. То есть, вместо базы данных users_db в БД пользователей будут созданы tenant1_users_db, tenant2_users_db
	Низкоуровневые элементы , относящиеся к уровню одной базы данных, не делятся, так как базы разные. Однако это все еще один инстанс, так что CPU и RAM делятся между тенантами
	
- На уровне инстансов БД
	Каждый тенант получает свой инстанс БД. То есть вместо одного инстанса БД пользователей будут "БД пользователей tenant1" и "БД пользователей tenant2". У каждой будет одна база данных users
	У каждого тенанта свой инстанс БД, так что ресурсы CPU и RAM у каждого тенанта будут свои 

Сравнивать будем критериям:
- Уровень изоляции тенантов
	Могут ли тенанты влиять друг на друга
- Стоимость добавления нового тенанта
	Насколько дорого добавить нового тенанта
- Масштабируемость по тенантам
	Насколько легко добавить нового тенанта
- Удаление тенанта
	Насколько легко удалить данные тенанта

Так как на каждой ферме может быть развернут лишь один тенант, то дополнительная изоляция данных на стороне Edge-агента не требуется. Единственное изменение: агрегированные метрики, посылаемые из Edge на платформу будут содержать tenant_id тенанта фермы
#### Изоляция на уровне схем БД

Представлена в C2_multi_1.puml

На уровне C2 отличается от решения, предложенного в **ADR-002: Архитектура платформы и Edge для управления фермой** добавлением ограниченного контекста тенантов: сервис работы с тенантами и его БД. 

Работа с тенантами выражается в следующем:
1) Токен, по которому идет работа через API GW теперь будет дополнительно содержать tenant_id - идентификатор тенанта
2) При аутентификации запросов сервис работы с пользователями будет не только проверять наличие пользователя, но и валидировать, что он является частью указанного в токене tenant
3) После успешной аутентификации работа с сервисами оборудования и животных будет идти с неймспейсами, созданными под нужный тенант 

#### Изоляция на уровне баз данных

На уровне C2 не отличается от решения из C2_multi_1.puml

На уровне C2 отличается от решения, предложенного в **ADR-002: Архитектура платформы и Edge для управления фермой** добавлением ограниченного контекста тенантов: сервис работы с тенантами и его БД. 

Работа с тенантами выражается в следующем:
1) Токен, по которому идет работа через API GW теперь будет дополнительно содержать tenant_id - идентификатор тенанта
2) При аутентификации запросов сервис работы с пользователями будет не только проверять наличие пользователя, но и валидировать, что он является частью указанного в токене tenant
3) После успешной аутентификации работа с сервисами оборудования и животных будет идти с базами данных внутри одного инстанса Postgres, созданными под нужный тенант 
#### Изоляция на инстансах БД

Представлена в C2_multi_2.puml

На уровне C2 отличается от решения, предложенного в **ADR-002: Архитектура платформы и Edge для управления фермой** добавлением ограниченного контекста тенантов(сервис работы с тенантами и его БД) и изменением подхода к работе с БД. Теперь на каждый тенант создается по 3 базы(пользователи, оборудование и животные), а соответствующие сервисы при взаимодействии со своей БД проходят через новый сервис DataSource Manager, который проксирует запрос в нужную БД

Работа с тенантами выражается в следующем:
1) Токен, по которому идет работа через API GW теперь будет дополнительно содержать tenant_id - идентификатор тенанта
2) При аутентификации запросов сервис работы с пользователями будет не только проверять наличие пользователя, но и валидировать, что он является частью указанного в токене tenant
3) После успешной аутентификации работа с сервисами оборудования и животных будет идти с инстансом БД, созданным под тенант через прокладку в виде DataSource Manager

#### Сравнение по выбранным критериям

 ##### Уровень изоляции тенантов
 
 - Изоляция на уровне схем БД
	 Самая высокая изоляция на уровне инстансов
	 Самая низкая изоляция на уровне схем БД
- Стоимость добавления нового тенанта
	Изоляция на уровне схем и БД имеют примерно одинаковую и небольшую стоимость, так как количество железа не изменяется
	Изоляция на уровне инстанса стоит дорого, так как растет количество используемого железа
- Масштабируемость по тенантам
	Изоляция на уровне схем и БД имеют примерно одинаковую и небольшую стоимость масштабирования - достаточно скриптов для создания схемы/БД
	Изоляцию на уровне инстанса масштабировать значительно сложнее, так как потребуется значительно больше DevOps активностей
- Удаление тенанта
	При изоляции на уровне схем БД удалить тенанта наиболее сложно из-за того, что в одной БД располагаются несколько тенантов
	В случае изоляции на уровне БД или инстансов, удаление сильно проще, так как нужно дропнуть базу целиком или удалить целый инстанс


#### Итого

В задании не сказано с какими клиентами планирует работать "АгроТех Х". Есть ли у них жесткие требования по безопасности и прочее.

С учетом того, что решение на инстансах усложняет и удорожает систему, а явная необходимость такого в ТЗ не отражена, считаю, что такой подход излишен.
В нашем случае на платформе хранятся только агрегаты данных, то есть данных не так много + с ними не так часто взаимодействуют. Кажется, что гибридный подход с изоляцией по схемам БД с возможностью вынести отдельного клиента в отдельную БД будет достаточен.

### 3.3 API для клиентов SaaS-платформы

#### Сервис пользователей

Коллекция: `/api/users`

##### Создание пользователя
```
POST /api/users  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>  
  
{   
    "name": "Вася",   
    "password": "Пароль",  
    "notify_to": "vasya@mail.ru"  
}
```

##### Получение пользователя

```
GET /api/users/{userId}  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```

##### Обновление пользователя

```
PUT /api/users/{userId}  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>  
  
{  
    "name": "Вася Пупкин",  
    "notify_to": "vasya_new@mail.ru"  
}
```
##### Удаление пользователя

```
DELETE /api/users/{userId}  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```

##### Авторизация (логин)

```
POST /api/users/token  
  
Tenant: <TenantId>  
  
{  
    "name": "Вася",  
    "password": "Пароль"  
}
```


#### Сервис работы с животными

##### Получение общей статистики

```
GET /api/animals 
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```

#### Сервис работы с оборудованием

##### Получение статистики оборудования

```
GET /api/devices  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```

##### Получение информации по устройству

```
GET /api/devices/{deviceId}  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```

##### Отправка политики на устройство

```
POST /api/devices/{deviceId}/policy  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>  
  
{  
    "policy": {  
        "feeding_interval": 4,  
        "temperature_threshold": 22  
    }  
}
```

#### Сервис подписок

##### Покупка подписки

```
POST /api/subscriptions  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>  
  
{  
    "plan": "premium",  
    "duration_days": 30  
}
```
##### Отмена подписки

```
DELETE /api/subscriptions/{subscriptionId}  
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```

##### Получение подписки тенанта

```
GET /api/subscriptions 
  
Authorization: Bearer <Token>  
Tenant: <TenantId>
```
