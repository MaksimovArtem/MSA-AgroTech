# ADR-003: Архитектура платформы без Edge для управления фермой

Автор: Максимов Артем

## 1. Контекст

Описание альтернативного решения, описанного в **ADR-001: Разработка вариантов решения**

Разрабатывается платформа управления фермами, включающая:
- сбор телеметрии с оборудования (датчики, исполнительные устройства)
- обработку видеопотоков (анализ состояния животных)
- агрегацию метрик
- генерацию уведомлений
- веб и мобильный интерфейсы

## 2. Требования

Требования к системе описаны в **ADR-001: Разработка вариантов решения**
В рамках этого документа требуется описать высокоуровневые контексты системы и взаимодействие между ними

Система должна:
- обрабатывать видеопотоки в реальном времени
- быть отказоустойчивой
- поддерживать асинхронную обработку событий
- работать в условиях нестабильной связи с фермами

## 3. Решение

Так как в заданиях 1-4 платформа разрабатывается для самой компании - можно использовать уже имеющийся у нее BI-модуль для агрегации и визуализации метрик. В рамках MVP и того, что явно это не обговорено, считается, что у него есть HTTPS интерфейс, способный получать метрики из внешних источников. До доработки этим интерфейсом мог пользоваться "Аналитик", работающий с BI-системой.

C2 диаграмма представлена в C2_alter.puml

Принято решение реализовать платформу по следующим признакам
### 1. Микросервисная архитектура

На бэкэнд стороне системы выделены следующие контексты:
- Работа с пользователями
- Работа с животными
- Работа с устройствами
- Отправка событий на BI-модуль компании
- Взаимодействие с устройствами на ферме

Особенности реализации:
- Каждый сервис изолирован и имеет собственную базу данных
- Публикуются события аудита/метрики и логи для BI-модуля

### 2. Frontend

- Web: React / Vue
- Mobile: React Native

Причины:
- Высокая скорость разработки
- Переиспользование экспертизы внутри команды(у "АгроТех Х уже есть веб-приложение на React")
- React Native обеспечивает мультиплатформенность (iOS + Android)

SEO не является критическим, так как система ориентирована на авторизованных пользователей.
### 3. Основной backend стек — Go

Причины выбора:
- Высокая производительность
- Эффективная работа с конкурентностью (goroutines)
- Низкое потребление памяти
- Быстрый старт контейнеров
- Интеграция с Kubernetes
- Простой деплой (статический бинарник)
### 4. Синхронное взаимодействие через REST

Для синхронного взаимодействия между:
- Frontend -> API Gateway
- API Gateway -> backend-сервисы

принят подход REST over HTTP/HTTPS.

Преимущества:

1) React / React Native нативно работают по HTTP
2) Простота в использовании и разработке
	- Читаемые URL
	- JSON
	- Легко тестировать (curl / Postman)
3) Низкий порог входа  
4) Независимость от клиента  

### 5. Асинхронное взаимодействие через брокеры (RabbitMQ)

Используются:
- Отдельный брокер для телеметрии оборудования (для работы с MQTT)
- Брокер доменных событий /событий после обработки видеопотока
	  На схеме они разнесены для удобства, отображения, но могут быть одним инстансом RabbitMQ

Причины:
- Снижение связности сервисов
- Нативная поддержка MQTT через плагин RabbitMQ
- Возможность масштабирования потребителей
- Устойчивость к временной недоступности сервисов
- Платформа не является сильно нагруженной, тк работает внутри "АгроТех Х"
### 6. Базы данных

- PostgreSQL для бизнес-данных
- S3 для хранения видео
    
Причины:
- Соответствие отраслевым стандартам
- Отделение структурированных данных от медиа
- Масштабируемость
### 7. Edge Gateway

Выделен отдельный Device Gateway, выполняющий  следующие функции:
- Приём видеопотока (RTSP)
- Приём телеметрии с устройств(MQTT)
- Пересылка данных на платформу для дальнейшей обработки

Причины:
- Изоляция взаимодействия с нестабильной средой
- Разграничение edge-логики и core-логики
- Прокладка между оборудованием на ферме и платформой

## 4. Альтернативы

### 1. Технология синхронного взаимодействия

gRPC и GraphQL отклонены, так как усложняют систему, не предоставляя функционала, который предоставляет REST

### 2. Основной язык для backend

Java не выбран потому что:
- лишний оверхэд для мелких сервисов из-за JVM.
- более сложное управление зависимостями и сборкой в микросервисной среде по сравнению с Go.


Python не выбран потому что:
- меньшая производительность и выше latency для сетевых сервисов.
- управление зависимостями и деплой более проблематично  по сравнению с Go.
